# Phase 4 Plan 1: Copy Specs Button and Health Colours

## Phase Goal

**As a** user, **I want to** copy my full spec sheet from Home and see at a glance when my disk or memory is running low, **so that** I can paste accurate specs anywhere and spot trouble without reading every number.

> Restated from ROADMAP.md `**Goal:** Copy-to-clipboard, health indicators, and project documentation` plus PROJECT.md's core value. The roadmap goal line is not itself in user-story form; no new capability is introduced by this wording. To ratify the wording in ROADMAP.md, run `/gsd-mvp-phase 4`.

## Objective

Add the Copy specs button (SPEC-07) and the amber/red health colours (SPEC-08) to the Home page that Phase 3 built.

Purpose: the tracer proves the whole copy path end to end (XAML button, click handler, one card model shared by the renderer and the text, clipboard, Copied feedback through the existing tick). Task 2 then expands the same card model with health brush keys, so the colours ride on the path the tracer proved.

Output: `UI/MainWindow.xaml` gains the `CopySpecs` button in the reserved right side of `HomeHeader`. `Akari.ps1` gains `Get-HomeModel`, `Get-HostLine`, `Get-SpecText`, `Copy-Specs`, `Get-DiskHealth`, `Get-RamHealth`, the `$script:CopiedUntil` state and one tick line; `Update-Home` renders from the card model.

4. New function `Get-HomeModel`, placed after `New-FailedSpecs` and before `Update-Home`. Move the six per-card blocks out of `Update-Home` (lines 645-713) into it, keeping every rule exactly as written. Instead of creating WPF elements, it returns an array of card descriptors in the fixed order CPU, GPU, RAM, Disk, Board, Windows. Each descriptor is a hashtable with these keys:
   - `Title`: the card title.
   - `Blocks`: an array of block hashtables. Each block has `Head` (the headline text) and `Rows`, an array of row hashtables. Each row has `Label`, `Value` (the display text, already formatted) and an optional `Key` (the brush key for the value; absent means Tx, and Task 2 fills it for two rows).
   - `Inline`: `$true` on the RAM card only.

   Rules carried over unchanged:
   - CPU: the Cores partial rule; Speed through `Fmt-Num $cpu.SpeedMHz '0.00' 'GHz' 1000`.
   - GPU: one block per adapter in read order. Rows are VRAM and Driver, plus Status only when it is not `OK`. A Failed group gives every block the head `Not available`. Zero adapters gives one block with head `Not available` and no rows.
   - RAM: the head is the total (or `Not available` when Failed); rows are Used and Free.
   - Disk: only the volume whose Drive equals `$env:SystemDrive`. The head is the drive plus two spaces and the label when the label is non-empty; rows are Free, Total and File system. Zero matches gives one `Not available` block with no rows.
   - Board: the head joins the non-sentinel Manufacturer and Product with one space, or is `Not available` when Failed or when nothing survives; rows are BIOS and Released.
   - Windows: the head is the Edition with a leading `Microsoft ` stripped (or `Not available` when Failed); rows are Version and Build.

   Read only `$script:SpecData.Specs`. Build every array with `@(...)` and append hashtables with `+=` so that a one-row or one-block array stays an array. Collect cards in a `[System.Collections.Generic.List[object]]` and return its `ToArray()`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Akari process → Windows clipboard | User-initiated: the spec sheet leaves the app and becomes readable by any program the user pastes into, or any program that reads the clipboard |
| spec read value → copied text | Strings that a compromised or malformed SMBIOS/WMI can supply are written into text the user pastes elsewhere |
| live values → health colour | A colour is a judgement drawn from numbers; a wrong judgement misleads the user about the machine's state |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Information disclosure | `Copy-Specs` / `Get-SpecText` in `Akari.ps1` | low | mitigate | Copying happens only on an explicit click. The text holds only what Home already shows: computer name, Maker · Model and the six card values. No serial number, UUID, product key, MAC/IP address or user name is read or written. The text goes to the local clipboard only, with no network call and no file write (prohibition, verified by the AST scan of the four functions). |
| T-04-02 | Tampering | Clipboard payload built by `Get-SpecText` | low | mitigate | The payload is set with `[Windows.Clipboard]::SetText`, so it is a single Unicode text format with no HTML or RTF flavour. A hostile spec string pastes as inert text and cannot inject markup into the paste target. |
| T-04-03 | Denial of service | `Copy-Specs` when another program holds the clipboard | low | mitigate | The clipboard call is wrapped in try/catch. Failure shows `Copy failed` for about 2 seconds and the app keeps running. Nothing escapes to the host's unhandled-exception guard, and no retry loop runs on the UI thread. |
| T-04-04 | Spoofing | `Get-DiskHealth` / `Get-RamHealth` health colours | low | mitigate | A colour is produced only when both numbers are numeric and the total is positive (D-12); sentinel or failed values are never coloured. The thresholds are pure functions verified at every boundary, so a missing reading cannot pass for a dangerous or a healthy one. |
| T-04-SC | Tampering | Package installation surface | high | accept | This plan installs nothing: Windows PowerShell 5.1 plus the inbox WPF/.NET Framework assemblies already loaded by `Akari.ps1:15` (`PresentationFramework` provides the clipboard API). No npm/pip/cargo install exists, so the package-legitimacy audit has zero rows. |
