# Phase 4 Plan 3: Close the Phase 3 Review Findings (WR-01, WR-02, WR-03)

## Phase Goal

**As a** user, **I want** the Home page never to get stuck dimmed and its CPU numbers and copied text to be right on every machine, **so that** the specs I see and copy are accurate and live.

> Restated from ROADMAP.md `**Goal:** Copy-to-clipboard, health indicators, and project documentation` plus PROJECT.md's core value ("if the specs are wrong or stale, the page fails its purpose"). The roadmap goal line is not itself in user-story form; no new capability is introduced by this wording. To ratify the wording in ROADMAP.md, run `/gsd-mvp-phase 4`.

## Objective

Fix the three open warnings from `03-REVIEW.md` so Home ships without known defects (04-CONTEXT D-16, D-17, D-18; the user's call: "lets just finish the work"):

- WR-01: a hung spec read must not leave Home dimmed for the whole session.
- WR-02: the dormant tweak-runner result harvest must not be able to overwrite `$script:SpecData`.
- WR-03: the CPU card must count every socket.

Purpose: the copy button (SPEC-07) and the health colours (SPEC-08) from plan 04-01 both read `$script:SpecData`. WR-01 keeps that data from freezing behind a hung read. WR-02 keeps it in the one shape both features expect. WR-03 makes the copied CPU line and the card true on multi-socket machines.

Output: changes to `Akari.ps1` only. Wave 2: this plan edits the same file as plan 04-01 and builds on its `Get-HomeModel`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WMI/CIM provider → background runspace | A provider can hang, which is outside the app's control; the read must stay bounded |
| background runspace → UI thread | Read results and abandoned pipelines cross only inside the 150 ms tick |
| tweak runspace → $script:SpecData | Before this plan, any finished tweak job that carried a result variable could write the shared Home data |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-07 | Denial of service | Tick spec-completion block, `Start-SpecRead` | medium | mitigate | Each read carries a `Deadline` 20 seconds ahead. Past it, the tick frees the slot, calls only the non-blocking `BeginStop`, and redraws Home undimmed with one log line. Every CIM call also has `-OperationTimeoutSec 10`. Verified with an uninterruptible 6-second hung pipeline: the tick returns in under 2 seconds. |
| T-04-08 | Tampering | `Invoke-Code` and the tick tweak-completion block | medium | mitigate | The result-variable path is removed, so a tweak job can no longer write `$script:SpecData`. An AST check confirms that every assignment to `$script:SpecData` is the initializer or lies inside the spec-completion block, which accepts only a hashtable with a `Specs` key. |
| T-04-09 | Tampering | CPU group in `Get-Specs` (data integrity of displayed and copied specs) | low | mitigate | Cores and threads are summed across every `Win32_Processor` instance, and the socket count is shown when above 1. Multi-socket machines therefore no longer under-report, and the copied text cannot misstate the hardware. Verified with a mocked two-socket read. |
| T-04-10 | Denial of service | `$script:SpecStale` (abandoned runspaces) | low | accept | A pipeline stuck in native code may never end; its runspace then stays referenced in `$script:SpecStale` until the app closes. That costs at most one runspace per 20-second timeout, and it keeps the UI thread from ever blocking. This is an accepted, bounded leak, not a crash. |
| T-04-SC | Tampering | Package installation surface | high | accept | This plan installs nothing: Windows PowerShell 5.1 plus the inbox .NET/WPF assemblies and the inbox CimCmdlets module. No npm/pip/cargo install exists, so the package-legitimacy audit has zero rows. |
</threat_model>
